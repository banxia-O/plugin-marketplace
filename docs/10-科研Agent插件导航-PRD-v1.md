## 0. 已冻结的产品决策

### 0.1 正式产品名

**插件百宝阁（科研版）**

定位副标题建议：

> 给科研 Agent 找趁手的工具

名称最终能否在微信公众平台注册，以平台名称审核结果为准；如名称被占用，只调整注册名称，不改变本 PRD 的产品定位。

### 0.2 一句话定位

**面向已经在使用 AI Agent 的中文科研人员，在微信里快速搜索、分类浏览可信的 MCP / Skill / Agent 工具，查看中文 `agent.md`，并把插件信息交给桌面 Agent 使用。**

其中：

- **AI Agent**：能够调用工具、读写文件或执行工作流的智能代理；本产品主要服务 Agent 使用者，而非仅使用普通对话式 LLM 的大众用户。
- **MCP（Model Context Protocol，模型上下文协议）**：让 Agent 以统一方式连接外部工具、数据源和服务的协议。
- **Skill**：供 Agent 调用或遵循的能力模块、指令或工作流能力。
- **agent.md**：插件百宝阁为 Agent 优化的中文使用手册，用于帮助 Agent 快速理解插件用途、安装方式、配置要求和验证步骤。

### 0.3 V1 只做这些

1. 搜索插件；
2. 首页展示 6 个科研高频分类快捷入口；
3. 提供“全部分类”，完整读取网站现有分类体系；
4. 浏览插件列表与插件卡片；
5. 查看插件详情与 `agent.md`；
6. 复制仓库地址 / `agent.md`，交给桌面 Agent；
7. 本地保存最近浏览；
8. 展示用户协议、隐私说明、数据来源与科研敏感信息提醒。

### 0.4 V1 明确不做

- 小程序内 AI 推荐；
- 开放式 AI 对话；
- AI 自动拆科研工作流；
- 排行榜 / 飙升榜；
- 「半夏精选 / 生物医药科研」独立专区；
- 小程序端普通用户上传插件；
- 邮箱注册；
- GitHub OAuth；
- 微信登录；
- 用户头像、昵称、手机号收集；
- 收藏跨设备同步；
- 积分、社区、评论；
- 微信内安装本地插件；
- 自动执行用户电脑 / VPS 命令；
- 患者数据上传、临床决策或诊疗建议。

### 0.5 V1 不登录

V1 不建立小程序用户账号体系。

理由：

- 搜索、分类、详情、复制和最近浏览均可匿名完成；
- 最近浏览可以仅保存在本机；
- 减少 `openid`、头像、昵称、手机号等个人信息处理；
- 减少登录态、鉴权和账号异常带来的开发量；
- 降低隐私合规和审核复杂度；
- 后续若 V2 需要收藏同步，再增加微信登录。

# 1. 与现有插件百宝阁的关系

## 1.1 产品关系

小程序是现有「插件百宝阁」的科研场景移动端入口，不另建一套插件市场。

```text
                        ┌─ React Web（现有）
                        │
Cloudflare D1 ← Worker API
                        │
                        └─ 微信小程序（新增）
```

### 核心原则

- **Cloudflare D1 继续作为唯一数据真源（Source of Truth）**；
- 网站和小程序读取同一套插件数据；
- 网站和小程序读取同一套分类数据；
- 网站和小程序读取同一套 Stars、审核状态、部署方式、许可证和 `agent.md`；
- 网站现有上传、审核、同步流程保持不变；
- 网站用户上传并通过审核的插件，会自然进入同一数据库，小程序无需单独同步；
- 小程序不维护第二份插件 JSON 或第二个数据库。

## 1.2 代码仓库关系

保持现有 monorepo：

```text
plugin-marketplace/
├─ docs/
├─ packages/
│  ├─ frontend/        # 现有 React 网站
│  ├─ miniapp/         # 新增：微信小程序
│  ├─ shared/          # 前后端共享类型 / 数据契约
│  ├─ worker/          # 现有 Cloudflare Worker API
│  └─ review-service/  # 现有审核与 agent.md 生成服务
├─ data/
└─ ...
```

要求：

- 小程序独立构建；
- 微信上传包只包含小程序构建产物和必要依赖；
- Web 前端源码、审核服务和无关脚本不得打入小程序包；
- `main` 分支和现有生产站在 PRD 冻结前不改；
- 开发均在 `feature/wechat-miniapp-v1` 进行。

# 2. 用户与使用场景

## 2.1 核心用户

V1 核心用户：

> **已经开始使用 ChatGPT / Codex / Claude Code / Gemini CLI / Hermes 等具备 Agent 或工具调用能力产品的中文科研人员。**

优先场景：

- 生物医学研究生；
- 青年科研人员；
- 科研型医生；
- 已经在电脑、WSL、服务器或 VPS 上使用 Agent 的技术型科研用户。

典型特征：

- 知道自己需要“查文献 / 读 PDF / 连数据库 / 操作 Zotero / 跑生信”等能力；
- 可以从插件名称、简介和分类大致判断用途；
- 更关心工具是否真实、是否维护、怎样部署、支持什么环境；
- 真正的安装与执行仍发生在电脑或服务器上的 Agent 中；
- 手机上需要的是快速查询和交接，而非完整开发环境。

## 2.2 非目标用户

V1 不重点服务：

- 只把 LLM 当聊天机器人使用的大众用户；
- 完全不了解也不使用 Agent 的用户；
- 希望小程序替自己完成完整科研分析的人；
- 希望上传患者病历或未脱敏研究数据的人；
- 希望在微信内直接安装本地 MCP 的用户。

# 3. 核心价值与主闭环

## 3.1 核心价值

**科研人员需要一个 Agent 工具时，不必在 GitHub、英文 README 和零散社区帖子之间来回找；微信里搜一下或按分类浏览，就能快速拿到已经整理过的插件信息和中文 Agent 手册。**

## 3.2 60 秒核心闭环

```text
打开「插件百宝阁（科研版）」
        ↓
搜索关键词 / 点击首页快捷分类
        ↓
浏览插件卡片
        ↓
进入插件详情
        ↓
查看用途、部署方式、Stars、审核状态、agent.md
        ↓
复制仓库地址或 agent.md
        ↓
粘贴给电脑上的 Agent
```

成功定义：

> 用户能在 60 秒内从“我需要一个工具”走到“我已经拿到一个可继续交给桌面 Agent 的真实插件”。

# 5. 首页 PRD

## 5.1 首页目标

用户打开后，立刻知道：

1. 可以直接搜插件；
2. 不知道插件名时，可以从常见分类进入；
3. 所有分类仍然可以完整查看；
4. 这是给科研 Agent 找工具的目录，而不是科研问答机器人。

## 5.2 顶部

展示：

**插件百宝阁（科研版）**

副标题：

> 给科研 Agent 找趁手的工具

不放：

- Banner 轮播；
- 飙升榜；
- 热门排行榜；
- 生物医药精选大卡片；
- 活动广告。

## 5.3 科研敏感信息轻提示

首页搜索框附近显示一条短提示：

> 请勿输入患者身份信息、未公开研究数据或其他敏感信息。

要求：

- 轻量展示，不遮挡搜索主流程；
- 首版即加入；
- 文案在搜索页和关于页保持一致；
- 不暗示平台可以安全接收上述敏感信息。

## 5.4 搜索框

占首页视觉优先级最高的位置。

占位提示：

> 搜插件、功能或科研场景

示例关键词：

- PubMed
- 文献
- 单细胞
- Zotero
- PDF
- 数据库

规则：

- 中文 / 英文均可；
- 空字符串不请求；
- V1 使用现有数据库关键词搜索；
- V1 不承诺自然语言理解；
- 搜索失败可重试；
- 无结果时推荐进入分类浏览。

## 5.5 最近浏览

有记录时显示，无记录时隐藏整个区块。

建议：首页最多展示最近 6 个，完整历史最多保存 20 个。

本地记录结构：

```ts
{
  slug,
  name,
  oneLiner,
  lastViewedAt
}
```

规则：

- 打开详情页即更新；
- 同一插件去重并置顶；
- 超过上限淘汰最旧记录；
- 用户可以清空；
- 只存本机；
- 不上传服务端；
- 不需要登录。

## 5.6 首页 6 个科研高频分类快捷入口

首页不新造“科研主题”数据库，也不建立第二套分类映射体系。

首页只从现有网站分类中挑 6 个科研高频分类做快捷入口：

1. **科研学术**
2. **信息检索**
3. **文件与文档**
4. **数据与数据库**
5. **AI 与模型**
6. **开发工具**

它们只是首页快捷入口，实际数据仍来自现有分类接口。

要求：

- 不把这 6 个分类写成独立数据表；
- 首页快捷入口可通过 slug 配置；
- 进入后仍使用现有分类页逻辑；
- 分类内子分类继续沿用网站现有结构；
- 后端分类变更后，小程序通过接口读取最新数据。

## 5.7 全部分类

6 个快捷入口下方提供明显的：

> **全部分类**

点击进入完整分类页。

全部分类必须直接读取现有：

```http
GET /api/categories
```

原则：

- 不在小程序复制整套分类数据；
- 不因为“科研版”而隐藏数据库中的其他分类；
- 网站新增或调整分类后，小程序无需重新维护第二份分类表；
- 首页 6 个只是快捷入口，完整分类体系仍与网站同源。

# 6. 搜索与列表

## 6.1 数据接口

优先复用现有：

```http
GET /api/plugins?q=...
```

现有查询能力包含：

- `q`
- `category`
- `subcategory`
- `deployMethod`
- `sort`
- `page`
- `pageSize`

因此 V1 原则上不为小程序另写一套搜索后端。

## 6.2 搜索结果排序

V1 保持现有服务端排序逻辑。

小程序不得自行制造与网站冲突的第二套综合评分。

未来如增加 AI 推荐，应在 V2 单独设计推荐服务，而非偷偷改变 V1 搜索含义。

## 6.3 插件卡片字段

列表卡片优先展示：

- 插件名；
- `oneLiner`；
- 主要分类 / 子分类；
- 部署方式；
- Stars；
- 审核状态；
- `agent.md` 状态（必要时）；
- 最近仓库更新时间（空间允许时）。

卡片不塞满全部元数据。

视觉目标：

> 一眼看懂“它大概干嘛、可信程度如何、能不能部署”。

## 6.4 空结果

文案建议：

> 暂时没找到匹配的插件，试试缩短关键词，或者从分类里找找。

提供：

- 返回修改搜索；
- 去全部分类。

不调用生成式 AI 猜测不存在的插件。

# 8. 插件详情页

## 8.1 核心信息

详情页展示：

- 插件名称；
- 一句话简介；
- 分类；
- 部署方式；
- 审核状态；
- `agent.md` 状态；
- Stars；
- 最近仓库更新时间；
- 支持平台；
- 许可证；
- 原作者；
- 原仓库地址；
- `agent.md`。

## 8.2 agent.md

`agent.md` 是 V1 的核心差异化内容。

说明文案：

> `agent.md` 是面向 AI Agent 优化的中文使用手册，帮助 Agent 快速理解插件用途、安装、配置和验证方式。

支持操作：

- 查看；
- 复制全文。

如为空：

> 该插件的 agent.md 暂待完善，可先查看原仓库说明。

不得在小程序端临时调用模型生成一个冒充正式 `agent.md` 的版本。

## 8.3 仓库地址

主要操作：

- **复制仓库地址**。

如微信环境允许且审核规则可接受，再提供明确的外部访问方式；复制功能必须独立可用，避免依赖外跳完成主闭环。

## 8.4 Stars

继续沿用现有生产逻辑：Worker 定时同步源 GitHub 仓库元数据。

当前仓库定时任务按每 4 小时同步一次设计，小程序只读取结果，不自行请求 GitHub API。

优点：

- 不增加小程序端 GitHub API 调用；
- 不暴露 Token；
- 网站与小程序 Stars 一致；
- 不制造双重同步任务。

# 9. 隐私、用户协议与科研数据边界

## 9.1 V1 数据最小化原则

V1 不主动收集：

- 微信昵称；
- 微信头像；
- 手机号；
- 通讯录；
- 精确位置；
- 相册；
- 麦克风；
- 患者资料；
- 用户科研原始数据。

V1 不登录，因此也不以 `openid` 建立产品账号体系。

## 9.2 本地数据

最近浏览保存在小程序本地 Storage。

用途仅为：

> 下次打开时快速找回最近看过的插件。

不上传最近浏览历史到服务器。

## 9.3 搜索输入

搜索关键词会发送至插件百宝阁 API 用于返回查询结果。

产品层必须明确提醒：

> 请勿输入患者身份信息、未公开研究数据或其他敏感信息。

搜索功能只需要插件关键词、功能词或科研场景词，不需要任何患者级信息。

## 9.4 用户隐私保护指引

上线前必须按照小程序**实际使用的接口、组件、SDK 和实际数据处理行为**填写微信公众平台《小程序用户隐私保护指引》。

产品侧提供：

- 关于页中的隐私说明；
- 可访问的《用户隐私保护指引》入口；
- 首页面向科研场景的敏感信息提醒。

工程侧原则：

- 若实际使用微信隐私相关接口 / 组件，则按微信平台要求完成声明及授权流程；
- 未声明的信息类型不得通过隐私接口收集；
- 不为了“以后可能用”而提前申请位置、相册、手机号等权限；
- 第三方 SDK 尽量少用，新增 SDK 前必须检查其隐私行为。

说明：页面上的隐私提示用于降低误输入风险，但**不能替代微信公众平台要求的正式隐私保护指引配置**。

## 9.5 用户协议

V1 提供简洁《用户协议》，至少说明：

- 本产品提供公开插件信息检索和整理；
- 插件实际安装、运行由用户及其 Agent 自行完成；
- 第三方插件由原作者维护；
- 用户应自行核验插件权限、许可证和适用性；
- 本产品不提供医疗诊断或临床决策；
- 禁止利用本产品处理违法内容或提交不应上传的敏感信息。

# 10. 数据来源、审核与版权

## 10.1 数据来源

核心数据来自现有插件百宝阁数据库，主要包括：

- 插件名称；
- 简介；
- 仓库链接；
- 分类；
- 部署方式；
- Stars；
- 仓库更新时间；
- 原作者；
- 许可证；
- 支持平台；
- 审核状态；
- `agent.md`。

## 10.2 网站上传流程继续保留

网站仍允许符合现有规则的用户提交插件。

小程序不展示上传入口。

数据流程：

```text
网站用户提交
   ↓
现有审核流程
   ↓
D1 插件数据
   ↓
Web / 小程序共同读取
```

小程序无需知道数据最初是开发者录入、网站投稿还是批量整理所得，只依赖审核后的统一插件数据。

## 10.3 第三方插件声明

详情页应明确：

- 原作者；
- 原仓库；
- 许可证（若数据中有）；
- 本站审核 / 整理状态。

不得暗示第三方插件由「插件百宝阁（科研版）」开发。

## 10.4 参赛溯源

开发阶段保留：

- Git commit；
- PRD 与设计决策；
- AI 辅助开发记录；
- 第三方依赖与许可证清单；
- 关键测试结果。

用于满足赛事对原创性、AI 使用合规与可追溯性的要求。

# 11. 技术架构

## 11.1 总体架构

```text
┌──────────────────────────────┐
│ 微信小程序                    │
│ packages/miniapp             │
│                              │
│ 首页 / 搜索 / 分类 / 详情     │
│ 最近浏览（本地 Storage）      │
└─────────────┬────────────────┘
              │ HTTPS
              ▼
┌──────────────────────────────┐
│ Cloudflare Worker API        │
│ 现有 /api/*                  │
└─────────────┬────────────────┘
              │
              ▼
┌──────────────────────────────┐
│ Cloudflare D1                │
│ 唯一数据真源                  │
└──────────────────────────────┘

现有 Web ────────────────┘
审核服务 ────────────────┘
```

## 11.2 API 复用

V1 优先直接复用：

```text
GET /api/health
GET /api/categories
GET /api/plugins
GET /api/plugins/:slug
GET /api/search
```

趋势榜接口不进入小程序 V1 页面。

现有注册、登录、投稿 API 不在小程序 V1 调用。

## 11.3 请求域名

上线前必须完成一次真机验证：

```text
微信小程序
   ↓
HTTPS request 合法域名
   ↓
Cloudflare Worker
```

要求：

- 使用正式 HTTPS 域名；
- 不把 localhost / IP 当作生产接口；
- 按微信公众平台当时的服务器域名规则配置；
- 当前域名备案情况不作为“默认一定可过”的假设；
- 若现有 API 域名无法满足平台要求，再准备新的合规 API 域名或中转方案。

CloudBase 不是 V1 默认依赖。

## 11.4 前端技术实现

默认优先尝试：

> Taro 4 + React + TypeScript

原因：现有项目为 React + TypeScript，便于复用类型、API 设计思想和部分业务逻辑。

但该技术选择属于工程决策，不需要产品负责人逐项确认。

开发前先做最小验证：

- 能在微信开发者工具编译；
- 能真机打开；
- 能请求测试 API；
- 页面跳转与 Storage 正常；
- 构建产物满足微信上传要求。

若框架在实际微信环境中出现明显阻碍，可在不改变本 PRD 产品行为的前提下调整实现方式。

## 11.5 shared 包复用原则

允许复用：

- TypeScript 类型；
- API 数据结构；
- 枚举；
- 纯函数业务逻辑。

谨慎复用：

- Zod runtime；
- Web 专用依赖。

禁止直接搬入：

- BrowserRouter；
- DOM API；
- `window` / `document`；
- Web CSS 布局代码；
- 仅浏览器可用的 Markdown / 图标实现。

目标：共享“数据和业务定义”，重写“小程序视图层”。

# 12. UI 设计原则

沿用 Web「清透、柔和、亲切、轻量」的视觉基因，但按微信移动端重新布局。

保留品牌特征：

- 淡紫主色；
- 白色卡片；
- 轻边框；
- 圆角；
- 清晰的标签层级；
- 青色作为次级交互色；
- 橙色仅用于少量强调。

不直接照搬 Web：

- 桌面双栏详情；
- hover 动效；
- 大面积 Hero；
- 复杂导航栏；
- PC 网格密度。

移动端优先：

- 单手操作；
- 点击区域足够大；
- 标题和主要动作首屏可见；
- 正文可滚动；
- `agent.md` 阅读体验优先于装饰。

# 13. 异常与降级

## 13.1 API 不可用

首页分类或搜索请求失败：

- 显示明确错误状态；
- 提供“重试”；
- 最近浏览仍可读取本地缓存；
- 不用假数据冒充线上结果。

## 13.2 搜索无结果

提供：

- 修改关键词；
- 全部分类入口。

## 13.3 插件详情失效

如插件已删除或 slug 无效：

> 这个插件暂时找不到了，可能已经下架或信息发生变化。

提供返回按钮。

## 13.4 agent.md 为空

仍展示插件基本信息和仓库地址，不阻断详情页。

## 13.5 Stars 同步失败

沿用数据库上一次成功同步值；前端不因此报废整个页面。

# 14. 性能与包体积

要求：

- 小程序包不包含 Web 源码；
- 不把完整插件库静态打进小程序包；
- 插件列表按 API 分页读取；
- 图片和图标控制体积；
- 大型 Markdown 解析依赖在引入前评估构建体积；
- 按微信开发者工具当前规则检查主包和总包；
- 若必要，详情页或 Markdown 能力可分包。

性能目标：

- 首页骨架可快速出现；
- 搜索后及时反馈加载状态；
- 长 `agent.md` 不阻塞整个页面首屏；
- 弱网下可明确看到加载 / 重试状态。

# 18. 关键风险

| 风险 | 影响 | 处理 |
|---|---|---|
| API 域名不满足微信生产要求 | 无法正式请求数据 | Step 0 真机验证，必要时使用新的合规 API 域名 |
| 小程序 ICP / 认证进度 | 延迟审核上线 | 与开发并行推进，预留返审时间 |
| Markdown 依赖过重 | 包体积或性能问题 | 先测体积，必要时轻量解析 / 分包 |
| Web 与小程序出现第二套分类 | 长期维护混乱 | 分类始终从现有 API 读取 |
| 复制 Web 组件导致兼容问题 | 开发返工 | 只复用数据 / 类型 / 业务定义，视图层重写 |
| 用户误填患者资料 | 隐私风险 | 搜索区显式敏感信息提醒，不提供文件上传 |
| 第三方插件失效 | 用户体验下降 | 显示仓库更新时间 / 审核状态，沿用定时同步 |
| 为比赛强塞 AI 导致审核复杂 | 延期 | V1 不接开放式 AI，V2 再评估 |
