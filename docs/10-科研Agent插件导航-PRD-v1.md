## 0. 产品决策摘要

### 0.1 一句话定位

**面向已经在使用 AI Agent 的中文科研人员，在微信里快速搜索和浏览可信的 MCP / Skill / Agent 工具，查看中文 `agent.md`，并把工具信息交给桌面 Agent 使用。**

其中：

- **AI Agent**：能调用工具、读写文件或执行工作流的智能代理；本产品主要面向 Agent 使用者，而非仅进行普通对话的 LLM 用户。
- **MCP（Model Context Protocol，模型上下文协议）**：让 Agent 以统一方式连接外部工具、数据源和服务的协议。
- **agent.md**：插件百宝阁为 Agent 优化的中文使用手册，目标是让 Agent 能快速理解插件用途、安装方式、配置要求和验证步骤。

### 0.2 V1 范围冻结

V1 只做四件事：

1. 搜索科研相关插件；
2. 按科研主题浏览插件；
3. 查看插件卡片与详情 / `agent.md`；
4. 本地保存最近浏览，方便再次打开。

明确不进入 V1：

- 小程序内 AI 推荐 / AI 对话；
- 排行榜；
- 「半夏精选 / 生物医药科研」独立专区；
- 普通用户上传插件；
- 邮箱注册、GitHub OAuth；
- 积分、社区、评论；
- 微信内安装插件或执行用户电脑命令；
- 临床决策、诊疗建议、患者数据处理。

### 0.3 与现有网站的关系

小程序不是另起一套插件库，也不复制数据库。

```text
                        ┌─ React 网站（现有）
                        │
Cloudflare D1 ← Worker API
                        │
                        └─ 微信小程序（新增）
```

- **Cloudflare D1 继续作为唯一数据真源（Source of Truth）**；
- 网站和小程序读取同一套插件、分类、Stars、审核状态、`agent.md`；
- 网站现有上传与审核流程继续工作；
- 用户在网站上传并通过审核的插件，会自然出现在小程序读取的数据中；
- 小程序 V1 不提供上传入口，因此不会引入第二套审核链路。

### 0.4 为什么 V1 暂不接 AI API

比赛主题是「与 AI 共生」，官方规程鼓励使用 AI、也鼓励接入微信 AI 生态，但并未要求所有作品必须在正式版中提供生成式 AI 问答。

当前小程序更核心的价值是：**让科研人员在手机端快速找到供 Agent 使用的真实工具，并把 `agent.md` / 仓库信息交给自己的 Agent。**

现阶段加入 AI 推荐会同时增加：模型成本、类目审核、隐私披露、错误推荐、接口稳定性和产品复杂度。因此 V1 优先保证可上线、可稳定使用、可获得真实反馈；当插件规模和搜索复杂度进一步上升后，再在 V2 增加 AI 推荐。

# 1. 背景与机会

## 1.1 已有产品底盘

「插件百宝阁」当前已经具备：

- React + Vite Web 前端；
- Cloudflare Worker API；
- Cloudflare D1 数据库；
- Cloudflare KV 缓存；
- 插件分类、搜索、详情；
- GitHub 仓库信息同步；
- Stars / 仓库更新时间等元数据；
- 插件审核状态；
- 中文 `agent.md`；
- 网站端插件投稿与审核工作流。

现有仓库采用 monorepo：

```text
packages/
├─ frontend        # React 网站
├─ shared          # 前后端共享 TS 类型与契约
├─ worker          # Cloudflare Worker API
└─ review-service  # 审核与 agent.md 生成
```

小程序建议新增：

```text
packages/
└─ miniapp         # 微信小程序，仅该目录构建产物提交微信
```

因此 GitHub 仓库可以继续保持一体化管理，**微信上传包不包含整个仓库，也不包含 Web 前端源码，只包含 miniapp 的构建产物及必要依赖。**

## 1.2 真实问题

科研人员使用 Agent 后，会很快遇到一个问题：

> “我的 Agent 能不能直接查 PubMed、读 PDF、操作 Zotero、跑数据库、读本地文件、做生信分析？”

答案往往是“可以，但需要正确的 Skill / MCP / 工具”。

目前这些工具散落在 GitHub、官方文档、社区帖子和各类插件目录中。科研人员常见困难包括：

- 不知道工具准确名称；
- 找到仓库后需要读英文 README；
- 不清楚是本地部署、远程服务还是两者皆可；
- 不清楚 Agent 是否能够使用；
- 不知道项目是否仍在维护；
- 不知道许可证和审核情况；
- 手机看到工具后，不方便快速交给电脑上的 Agent。

现有插件百宝阁已经解决了“集中整理 + 中文说明 + agent.md + 审核”的大部分问题，小程序解决的是**科研场景中的移动端快速查询入口**。

# 2. 目标用户

## 2.1 唯一核心用户

V1 核心用户：

> **已经开始使用 ChatGPT / Codex / Claude Code / Gemini CLI / Hermes 等具备 Agent 或工具调用能力产品的中文生物医学研究生、青年科研人员和科研型医生。**

典型特征：

- 知道自己大概要做什么；
- 对 MCP / Skill 有模糊认知或已经用过少量插件；
- 不需要从零解释“AI 是什么”；
- 更关心工具是否真实、能否部署、适合哪个环境；
- 手机端常用于随手查资料，但真正执行工作仍在电脑 / VPS / Agent 环境完成。

## 2.2 非目标用户

V1 明确不主要服务：

- 只把 LLM 当普通聊天机器人的大众用户；
- 完全不使用 Agent 的人；
- 希望小程序直接替自己完成科研分析的人；
- 希望上传患者隐私数据并获得诊疗建议的人；
- 希望在微信中直接安装、运行本地 MCP 的用户。

这不是大众 AI 教程，也不是科研聊天机器人。

# 3. 核心价值与 60 秒闭环

## 3.1 核心价值

**需要一个工具时，科研人员不必打开 GitHub 四处找仓库；微信里搜一下，就能拿到已经整理过的插件信息和 Agent 使用手册。**

## 3.2 主闭环

目标：新用户在 60 秒内完成一次有效工具发现。

```text
打开小程序
   ↓
输入关键词 / 点击科研主题
   ↓
浏览插件卡片
   ↓
进入插件详情
   ↓
查看 agent.md / 部署方式 / Stars / 审核状态
   ↓
复制仓库地址或 agent.md
   ↓
交给电脑上的 Agent
```

### 示例

用户搜索：`文献`。

结果中看到：

```text
PubMed MCP
一句话简介……

远程 / 本地       ⭐ 3.2k
科研学术 · 文献检索
基础审核通过
```

点击详情后可以看到：

- 这个插件做什么；
- 支持平台；
- 部署方式；
- Stars；
- 许可证；
- 原作者；
- 最近更新时间；
- 审核状态；
- `agent.md`；
- 仓库地址。

核心动作：

- `复制 agent.md`
- `复制仓库地址`

随后用户在桌面 Agent 中粘贴内容并继续工作。

# 5. 首页 PRD

## 5.1 首页目标

打开后马上回答两个问题：

1. 我可以搜什么？
2. 不知道具体插件名时，我可以从哪些科研主题开始看？

## 5.2 首页结构

### A. 顶部

- 小程序名称 / Logo；
- 一句轻量副标题，例如：`给科研 Agent 找趁手的工具`；
- 不放排行榜、Banner 轮播、活动广告。

### B. 搜索框

占据首页最重要位置。

占位提示建议：

> 搜插件、功能或科研场景

示例关键词：

- PubMed
- 文献
- 单细胞
- Zotero
- PDF
- 数据库

交互：

- 点击搜索后进入搜索结果页；
- 支持中文 / 英文关键词；
- 空字符串不发送请求；
- 搜索请求失败时允许重试；
- 无结果时提示缩短关键词或通过主题浏览。

V1 继续使用现有数据库关键词搜索，不承诺语义搜索或自然语言理解。

### C. 最近浏览

有历史时显示，无历史时整块隐藏。

建议最多展示最近 6 个插件卡片，完整记录最多保存 20 条。

最近浏览只存本机：

```ts
{
  slug,
  name,
  oneLiner,
  lastViewedAt
}
```

规则：

- 打开插件详情即更新；
- 同一插件去重并置顶；
- 超过 20 条淘汰最旧记录；
- 用户可清空；
- 不需要登录；
- 不同步到服务端。

### D. 科研主题

V1 主题是**小程序展示层的科研场景导航**，不新建第二套数据库分类。

推荐首版 6 个主题：

| 主题 | 现有分类映射 | 说明 |
|---|---|---|
| 文献与证据 | `research / literature` | PubMed、学术检索、全文获取等 |
| 生物信息 | `research / bioinfo` | 基因、蛋白、单细胞、组学工具 |
| 医学资源 | `research / medical` | 医学数据库、药物信息等 |
| 数据处理 | `data / processing` | 数据清洗、转换、导入导出 |
| 统计与计算 | `research / math` | 数学、统计、计算工具 |
| 科研笔记 | `office / notes` | Zotero / Obsidian / Notion 等知识工作流相关工具 |

主题只是 UI 聚合入口；数据库继续使用现有 `categories / subcategories / plugin_categories`。

如某主题当前没有足够插件，可在上线前隐藏，不为了填满主题而加入低质量条目。

# 6. 搜索结果页

## 6.1 数据来源

优先复用现有：

```http
GET /api/plugins?q=...
```

现有 `PluginListQuery` 已支持：

- `q`
- `category`
- `subcategory`
- `deployMethod`
- `sort`
- `page`
- `pageSize`

因此 V1 原则上不需要为了小程序重写搜索后端。

## 6.2 搜索卡片字段

卡片保持比 Web 更窄，只展示判断是否值得点开的信息。

必显：

- 插件名称；
- `oneLiner` 一句话简介；
- 分类标签；
- 部署方式；
- Stars。

建议显示：

- 审核状态；
- `agent.md` 是否可用。

不在列表卡片堆叠：

- 完整作者信息；
- License 详情；
- 支持平台完整列表；
- 长 README；
- 下载量 / 点赞量等对科研选工具帮助较弱的信息。

## 6.3 排序

V1 默认沿用原站的 `comprehensive` 综合排序。

Stars 只是项目成熟度 / 社区关注度信号之一，不展示“Stars 高 = 推荐更好”的误导文案。

暂不在小程序增加：

- 飙升榜；
- 30 天 Star 增量榜；
- 人工“热门推荐”。

# 7. 插件详情页

## 7.1 页面优先级

科研用户进入详情页主要想判断三件事：

1. 它能不能做我要的事；
2. 我的 Agent / 环境能不能用；
3. 我怎么把它交给 Agent。

因此移动端详情信息顺序建议：

### 第一屏

- 插件名称；
- 一句话简介；
- 分类；
- 部署方式；
- 审核状态；
- Stars；
- `复制仓库地址`；
- `复制 agent.md`（有 agent.md 时）。

### 第二段：agent.md

`agent.md` 是小程序的核心内容，不把它降级为折叠在页面最底部的附属材料。

显示要求：

- 支持常见 Markdown 标题、列表、代码块；
- 移动端代码块可横向滚动；
- 渲染失败时至少可回退为纯文本；
- 不执行 Markdown 中的任意 HTML / JS；
- 长内容按性能情况考虑折叠或分段渲染。

### 第三段：元数据

- 支持平台；
- License；
- 原作者；
- 原仓库；
- 仓库最近更新时间；
- `agent.md` 状态；
- 审核状态。

## 7.2 外部 GitHub 链接

微信小程序对任意外链打开能力存在平台限制，因此 V1 不把“直接打开 GitHub 网页”作为唯一主动作。

必须提供：

- 复制仓库地址；
- 复制 `agent.md`。

若后续确认 WebView / 业务域名可合法打开指定页面，再作为增强能力，不影响主闭环。

# 8. 数据与后端

## 8.1 数据唯一真源

继续使用现有 D1。

核心现有表包括：

- `categories`
- `subcategories`
- `plugins`
- `plugin_categories`
- `users`
- `ledger`
- `submissions`

小程序 V1 只读取公开插件相关数据，不另建“微信插件表”。

## 8.2 数据同步

现有 Worker 已有 GitHub 仓库 metadata 定时同步任务。

当前 Cron：

```text
0 */4 * * *
```

即约每 4 小时执行一次仓库元数据同步。

V1 直接继承该机制，不新增第二个“小程序 Stars 刷新任务”。

因此网站与小程序读取到的 Stars / 更新时间保持同源。

## 8.3 网站上传与小程序展示

```text
网站用户投稿
   ↓
现有 submissions / review-service
   ↓
通过后写入 plugins / 分类
   ↓
Web 与小程序共同读取
```

小程序不提供普通用户上传页面。

“只有开发者可以上传”在 V1 中的实际实现方式是：开发者继续通过现有网站 / 管理流程维护数据，而不是在小程序里另做一个隐藏上传后台。

# 9. 登录、用户协议与隐私

## 9.1 V1 不强制登录

搜索、主题浏览、插件详情、最近浏览全部可以匿名完成。

因此 V1 **不把微信登录作为核心流程前置条件**。

好处：

- 首次打开无登录弹窗；
- 不需要头像 / 昵称 / 手机号；
- 不增加用户数据库同步；
- 隐私收集范围更小；
- 减少审核和后端复杂度；
- 最近浏览本来就可以本地完成。

## 9.2 V1 明确不主动收集

- 手机号；
- 微信头像；
- 微信昵称；
- 精确位置；
- 通讯录；
- 相册；
- 麦克风；
- 摄像头；
- 患者身份信息；
- 未公开科研数据。

如果未来新增收藏同步 / 多设备同步，再评估：

```text
wx.login()
   ↓ code
Cloudflare Worker
   ↓ 微信 code2Session
   ↓ openid → 内部 user_id
```

届时再更新隐私保护指引和后端用户模型，不提前塞进 V1。

## 9.3 用户协议

小程序提供独立《用户协议》，至少说明：

- 产品用于检索和展示第三方 Agent 工具信息；
- 第三方插件由各自作者维护；
- Stars / 更新时间来自公开仓库信息；
- 插件使用、安装、授权和数据访问风险由用户在实际环境中确认；
- 本产品不提供医疗诊断、治疗建议；
- 禁止上传 / 输入患者身份信息或其他敏感数据（V1 本身没有上传入口，但协议保留边界）；
- 数据来源、第三方许可证与版权归属。

## 9.4 小程序用户隐私保护指引

正式上线前，在微信公众平台根据小程序**真实调用的接口和真实采集的数据**填写隐私保护指引。

PRD 原则：

> 能不采集就不采集；实际没有调用的权限，不为了模板完整而声明采集。

开发阶段需单独核对：

- 微信当前隐私保护指引配置要求；
- 实际调用 API 对应的隐私信息类型；
- 是否触发隐私授权弹窗；
- 第三方 SDK 是否产生额外采集。

未经核对，不在代码中加入广告、统计 SDK、设备指纹或第三方登录。

# 10. 网络、域名与 Cloudflare

## 10.1 推荐主链路

```text
微信小程序
   ↓ HTTPS
独立 API 域名
   ↓
Cloudflare Worker
   ↓
D1 / KV
```

不使用 CloudBase 作为必选中转层。

## 10.2 域名风险门槛

当前已有公开域名，但尚未备案，源站位于首尔。

因此开发前必须实际验证：

1. 该 API 域名能否在微信公众平台配置为合法 `request` 域名；
2. HTTPS / TLS 是否符合要求；
3. 域名备案要求是否会卡正式审核；
4. Worker 路由是否可以稳定从中国大陆访问。

**在微信公众平台验证通过前，不把“未备案境外域名可直接用于正式版”写成已解决事实。**

Plan A：现有 Cloudflare Worker + 新 API 子域名。

Plan B：若合法域名配置受备案限制，使用已满足微信要求的 API 域名 / 反向代理接入现有 Worker。

CloudBase 只有在确有必要时再使用，不因为“小程序”三个字就复制一套云函数和数据库。

- 微信开发者工具构建 / 真机验证

理由：现有 Web 已使用 React + TypeScript，业务模型和开发心智可以延续。

但 V1 不直接搬 Web DOM 组件。以下 Web 能力只能作为逻辑参考：

- `BrowserRouter`
- `window`
- `<a>`
- Web CSS hover
- `react-markdown`
- DOM 依赖 UI 库

小程序重新实现 View 层。

## 11.3 `shared` 复用原则

优先复用：

- TypeScript 类型；
- 枚举；
- API 请求 / 响应结构；
- category / plugin 数据模型。

谨慎复用运行时依赖。

现有 `@ppx/shared` 使用 Zod；小程序 V1 优先使用类型级复用，避免为了少量类型把不必要的 runtime 全塞进主包。

若实测构建体积明显增加，再拆：

```text
@ppx/types
@ppx/contracts
```

不在 PRD 阶段提前重构。

## 11.4 包体积目标

平台硬限制以开发时微信官方文档和开发者工具提示为准。

项目内部工程目标：

- 主包尽量控制在 1.5 MB 以内；
- 不把完整插件 JSON / Markdown 数据打入代码包；
- 插件内容按需通过 API 获取；
- 图片尽量使用小体积本地资源或合法 CDN；
- 非首屏页面可根据实测决定是否分包；
- 不引入大而全 UI 框架。

仓库整体大小不等于小程序上传包大小。

# 13. 异常与降级

显示：

`agent.md` 回退为安全纯文本。

## 13.5 GitHub 本身不可访问

不影响小程序读取 D1 中已有元数据和 `agent.md`。

用户仍可复制仓库 URL，稍后在可用网络环境打开。

- [ ] Markdown 异常有纯文本降级；
- [ ] 原 Web 路由和页面行为不因小程序代码而变化。

- 新用户从打开到复制一个插件信息，目标 ≤ 60 秒；

- `packages/miniapp` 可独立安装 / 构建；
- 小程序构建产物不包含完整插件数据库；

- Secret 不进入小程序包；

# 18. 开发顺序（Step by Step）

PRD 评审通过后按以下顺序开发，避免一次性大改：

### Step 0｜上线门槛验证

- 小程序账号 / AppID 可用；
- 公众平台类目确认；
- API 合法域名验证；
- HTTPS 真机请求成功；
- 小程序构建体积 POC。

若这一层失败，不进入大规模 UI 开发。

### Step 1｜工程骨架

只新增 `packages/miniapp`，跑通微信开发者工具 Hello World。

### Step 2｜API 只读连接

只实现：

```text
/api/health
/api/categories
/api/plugins
/api/plugins/:slug
```

先验证真实数据，不做 UI 美化。

### Step 3｜搜索闭环

首页搜索 → 搜索结果 → 详情 → 复制仓库地址。

这是第一个可用版本。

### Step 4｜agent.md

实现安全 Markdown / 纯文本显示与复制。

### Step 5｜主题

加入 6 个科研主题，复用现有 category / subcategory。

### Step 6｜最近浏览

加入本地 storage，不引入登录。

### Step 7｜视觉迁移

把 Web 的淡紫品牌系统转换为微信移动端 UI。

### Step 8｜隐私 / 协议 / 审核准备

按实际调用能力填写隐私保护指引，完成用户协议、数据来源和免责声明。

### Step 9｜真机测试与灰度

至少 Android + iOS 真机，测试弱网、无结果、长 agent.md、复制、返回栈。

### Step 10｜正式上线 + 用户反馈

争取在比赛提交截止前至少保留 2–3 周真实运营时间。

# 21. 风险清单

| 风险 | 等级 | 应对 |
|---|---:|---|
| 未备案域名无法作为正式 request 域名 | 高 | Step 0 立即实测；准备合规 API 域名 Plan B |
| 小程序审核 / 类目返审 | 高 | V1 不做生成式 AI 问答；提前提审 |
| 包体积超限 | 中 | 不打包插件数据；少依赖；先 POC |
| Markdown 包过大或兼容差 | 中 | 选择轻量渲染；纯文本降级 |
| GitHub 在部分网络不可访问 | 中 | 小程序主要读取 D1；复制 URL 作为交接 |
| 原站被小程序改动影响 | 高 | 独立 `packages/miniapp`；共享数据契约，不重写 frontend |
| 搜索关键词能力有限 | 中 | V1 接受边界；主题补充发现；V2 再语义搜索 |
| 科研主题当前插件数量不足 | 中 | 上线前按真实数据决定显示，不硬凑 |
| 用户误以为是医疗工具 | 中 | 详情 / 协议明确：工具导航，不提供诊疗建议 |
